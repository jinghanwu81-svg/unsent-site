## 1. 一句话定义

Unsent 是一个面向手机使用场景的情绪表达与陪伴产品原型，让用户在想联系某个人、还有话没有说完，或希望整理心情时，先把话写下来，再决定下一步。

当前原型通过「信箱、说说、小灯」三个空间，串联即时表达、文字保留和主动记录。聊天使用本地预设回复，尚未接入真实 AI。

## 2. 问题与机会

本项目围绕以下问题假设展开，尚不能视为用户研究结论：

- 用户在想表达的当下，可能尚未确定是否要把话发给对方，需要一个暂时安放文字的空间。
- 用户有时需要倾诉，有时需要安慰，有时希望梳理想法，对回应方式的期待可能不同。
- 零散表达之后，用户可能希望保留自己的文字，并回看某些日子的主观记录。

因此，原型尝试提供一条轻量路径：先表达，按需保留，主动记录。是否减少联系冲动、缓解情绪或促进长期使用，均有待进一步验证。

## 3. 目标用户与使用场景

### 3.1 初步目标用户

希望整理人际关系中的未尽表达，或暂时安放当下心事的用户。当前未通过访谈或行为数据确认核心人群，不预设年龄、性别或临床心理状态。

### 3.2 典型场景假设

| 场景 | 用户当下的需要 | 原型提供的入口 |
| --- | --- | --- |
| 很想联系某个人，但还没决定是否发送 | 先写下想说的话，留出考虑时间 | 说说、信箱 |
| 一段话没有写完，暂时不想继续 | 保留内容，之后继续编辑 | 信箱草稿 |
| 想倾诉，但不希望立即收到建议 | 选择更符合当下期待的回应方式 | 听我说说 |
| 希望被安慰，或梳理自己的期待 | 选择示例陪伴方式，体验交互方向 | 安慰一下、一起想清楚 |
| 希望记录某天想联系对方的冲动次数 | 主动填写，并按日期回看 | 小灯 |

## 4. 产品价值主张

给尚未准备发送的话一个可以停留的位置，让用户保有表达、保留和是否联系对方的选择权。

三个空间的分工如下：

- **信箱：保留表达。** 将文字存为草稿或未寄出的信，支持再次编辑和回看。
- **说说：提供表达入口。** 通过三种示例陪伴方式，探索不同回应风格的交互体验。
- **小灯：呈现主动记录。** 以日历和灯光展示用户填写的冲动次数，帮助回看记录。

小灯亮度是当前原型的视觉映射，不代表对用户的评价。该设计是否会带来压力、误解或挫败感，需要专门验证。

## 5. 当前阶段目标

本阶段以验证产品概念与关键使用流程为主：

1. 用户能否理解三个空间各自的用途。
2. 用户能否完成「表达 → 将自己的文字收进信箱 → 再次查看」的流程。
3. 用户是否理解草稿、已保存信件与临时对话的区别。
4. 用户能否正确理解小灯记录的是手动填写的冲动次数，以及「未记录」与「零次」的差别。
5. 用户是否理解当前聊天只是示例回应，并能清楚描述自己希望获得的陪伴方式。

当前 Demo 可用于交互走查和概念反馈，不能据此证明真实 AI 陪伴质量、长期留存或情绪改善效果。

## 6. 当前版本范围

以下为项目 README 描述的现有能力；本次文档整理不等同于完成新一轮功能验收。

| 模块 | 当前范围 | 主要限制 |
| --- | --- | --- |
| 信箱 | 新建、编辑、保存信件；关闭时保留草稿；按状态筛选；接收对话中用户写下的文字 | 保存在当前浏览器，无云同步与导出恢复能力 |
| 说说 | 三种陪伴方式、预设示例回复、新对话、将用户文字收进信箱 | 无真实 AI、无上下文理解能力；对话刷新后重置 |
| 小灯 | 切换月份、选择日期、记录冲动次数、首次确认零次、展示亮度分档 | 未来日期不可记录；当前无更正或删除记录界面 |
| 基础体验 | 中文界面、移动端布局、底部三入口导航 | 具体设备和浏览器兼容性仍需记录验收结果 |

## 7. 体验原则

- **降低表达门槛：** 允许从一句话开始，不要求用户先组织完整叙述。
- **保留用户选择：** 是否继续写、保留文字或联系对方，由用户决定。
- **清楚说明能力：** 区分示例回应与真实 AI 能力，区分临时对话与持久保存。
- **避免评价式反馈：** 记录用于回看，不将冲动次数包装成个人优劣或康复评分。
- **说明数据边界：** 本地保存不等于永久备份，也不等于加密存储。

现有视觉方向为暖白纸色、嫩绿与淡紫配色，配合信封和小灯意象。是否符合用户感受，应以反馈验证。

## 8. 核心假设与验证建议

以下是下一阶段建议，尚未执行。可先邀请少量符合场景的体验者进行定性走查，再根据问题决定是否扩大验证。

| 假设 | 建议验证方法 | 需要记录的证据 |
| --- | --- | --- |
| 用户能够理解三个空间的分工 | 首次体验时请用户描述各入口用途 | 理解偏差、犹豫位置、是否需要解释 |
| 从表达转到保留文字的流程自然 | 请用户完成一段表达并收进信箱，再次打开 | 完成情况、卡点、内容保留是否符合预期 |
| 三种陪伴方式有可理解的差异 | 请用户选择方式并解释期待，体验后反馈 | 选择理由、期待与示例之间的落差 |
| 小灯不会被误解为行为监测或评分 | 请用户解释零次、未记录和不同亮度 | 误解、压力感、不愿记录的原因 |
| 用户理解本地数据与聊天保存边界 | 请用户预测刷新或更换设备后会保留什么 | 错误预期、需要加强说明的位置 |

验证前定义具体任务和判定方式，验证后记录原始观察与结论。当前不填入未经测量的完成率、满意度或效果数据。

## 9. 约束与待决问题

### 9.1 已知约束

- 当前采用原生 HTML、CSS 和 JavaScript，可通过静态服务器运行。
- 信件、草稿和小灯记录使用浏览器 localStorage。
- 数据受浏览器和站点来源限制；更换端口、域名、设备或浏览器不会自动迁移。
- 清除网站数据会造成记录丢失；本地存储不提供加密保险箱式保护。
- 当前没有账号、后端或 AI 接口，本版本不会主动上传这些记录。

### 9.2 待决问题

- 哪一类使用场景最有持续需求，是否需要进一步收窄目标用户？
- 「说说」作为默认入口是否符合用户期待？
- 小灯的亮度规则是否易懂，是否需要更中性的表达方式？
- 日历记录的更正、删除，以及数据导出是否应优先补充？
- 如果接入真实 AI，需要如何定义回应边界、数据处理方式与质量标准？

以上问题进入后续需求评估，不在 Brief 中预先宣布为已确定方案。
